# Public search runtime parity

This DB-free runner checks the merged public search comparison helper against a
manually fixed golden vector set. It is intended to expose normalization,
projection, query-byte, and UTF-16 ID order-key behavior as runtime evidence
for a future stored-projection producer.

The runner imports
`lib/services/public-course-search-comparison.ts`; it does not copy the
implementation into the verification code. The oracle values in `vectors.ts`
are fixed independently of that helper. The vector set is
`public-search-runtime-parity.v1`.

Run from the repository root with an explicitly selected Node executable:

~~~
<node-executable> --import tsx verification/public-search-runtime-parity/run.ts
~~~

The runner writes JSON to stdout and diagnostics to stderr. To retain a local
result file without overwriting an existing file:

~~~
<node-executable> --import tsx verification/public-search-runtime-parity/run.ts --output verification/public-search-runtime-parity/runtime-result.json
~~~

An existing result can be compared with a second runtime using
`--compare <json-file>`. The comparison excludes runtime metadata but requires
the source, vector, lockfile, contract, and ordered vector IDs to bind first;
it then compares every actual value or error classification. Golden oracle
validation is also required, so two identical wrong outputs cannot produce a
parity PASS.

## Vector coverage

- NFKC, trim, Korean-locale lowercase, ASCII/Korean, fullwidth and
  compatibility characters, composed/decomposed U+00E9, Unicode spaces,
  internal spacing, literal `%`, `_`, and backslash.
- Omitted and empty query, exact 48-byte and over-limit queries, normalization
  before the byte limit, UTF-8/UTF-16 length differences, and case expansion.
- The five stored projection fields in contract order, explicit field
  boundaries, empty middle fields, internal field spacing, query containment,
  and a stored value above the query byte limit.
- ASCII, Korean, BMP-boundary, valid non-BMP, prefix/length, NUL, empty,
  non-string, and malformed-surrogate IDs.
- Comparison, normalizer, ID-order-key, and query-limit version values.

The runner reports the actual checkout commit, comparison-source blob and
SHA-256, vector blob and SHA-256, lockfile blob and SHA-256, runtime
version/ICU/Unicode/V8/platform/architecture, locale support, each vector's
escaped value or error classification, oracle result, and executed/pass/fail/
skip totals. Runtime metadata is kept separate from semantic output
comparison. `compare.ts` exists because artifact-level comparison must handle
missing results, failed jobs, binding mismatches, ordered ID/count checks, and
vector-level expected/actual differences independently of job aggregation.

## Independent oracle review

The 40 expected values are fixed literals in `vectors.ts`; they are not
generated by the product helper, the runner, or either runtime. The review
checked the Unicode-dependent boundaries against the official Unicode 17.0
UCD and UAX #15:

- NFKC uses compatibility decomposition followed by canonical composition:
  <https://www.unicode.org/reports/tr15/>.
- U+0130 has the unconditional lowercase mapping U+0069 U+0307, and the
  fullwidth/NBSP compatibility mappings used by the vectors are in
  <https://www.unicode.org/Public/17.0.0/ucd/SpecialCasing.txt> and
  <https://www.unicode.org/Public/17.0.0/ucd/UnicodeData.txt>.
- Unicode 17.0 defines surrogate pairs, rejects isolated surrogate code units
  as well-formed UTF-16, and identifies U+0000 as a control/scalar value:
  <https://www.unicode.org/versions/Unicode17.0.0/core-spec/chapter-3/>.

The fixed-width ID key itself is a product contract over JavaScript UTF-16
code units; the Unicode sources validate the scalar/surrogate boundaries but
do not define this application encoding. NUL is therefore tested only through
the pure JavaScript helper, not through a database. The vector set separates
normalization, projection/field boundaries, query UTF-8 byte limits, ID key
encoding, error classes, and version constants. No duplicate cases were added
only to increase the count.

## Runtime provenance and limits

The dedicated workflow runs exact Node 22.13.0 and 24.19.0 jobs on the same
Linux runner family, installs the existing lockfile with the repository's
setup-node/npm pattern, and compares their artifact results. Pull requests
checkout the final PR head explicitly; main pushes checkout `github.sha`.
This worktree has one executable local runtime, Node 24.19.0, with ICU 78.3,
Unicode 17.0, V8 13.6.233.17-node.51, and ko-KR locale support. No alternate
local Node runtime was installed or downloaded, so local execution alone does
not establish cross-runtime parity.

Existing helper tests cover direct contract assertions plus adapter,
repository-boundary, input-error, and sorting behavior in a normal test
runtime. This runner directly exercises the pure comparison functions with
fixed golden outputs and records runtime provenance; the matrix compares
per-vector actual values/errors across runtimes. It is not a replacement for
those helper tests and does not provide database/provider or cross-OS
coverage.

This verification does not prove all-Unicode equivalence, database collation
parity, PostgreSQL or D1 NUL storage support, runtime pinning, backfill
compatibility, provider parity, or writer integration. It does not modify
the product helper, adapter, schema, provider, cursor, package scripts, or
dependency lockfile.
